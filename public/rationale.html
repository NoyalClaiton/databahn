Design Rationale, Source Onboarding

Ten sources, two hours, zero SMEs

The brief names six problems: too many clicks, no guidance, SME dependency, weak hierarchy, unclear navigation, and an unmet ten-sources-in-two-hours goal. All six share one cause: every screen asked the customer to know something Databahn already knew. The fix, applied consistently: guessed and shown as a default, not asked as a blank field; explained in place, not filed in a knowledge base; built once as a shared shape, not rebuilt screen by screen for every connector.

01

Assumptions

This covers everyone from a first-time analyst to an admin onboarding their tenth source in one sitting, treated as one group, not two. Defaults help the beginner get through a screen with no prior knowledge. Progressive disclosure and session memory help the power user move faster on source ten than source one.

02

Key decisions

01

Guessed defaults, not blank fields

Cruz pre-fills or pre-selects wherever a plausible default exists. The customer confirms rather than configures from zero, the biggest click-reduction lever in the redesign.

Built: Palo Alto's log-type step pre-selects 10 of 13 by detection value, with a running GB/day estimate that updates live as it's toggled. Sentinel defaults to OAuth over a manual key; Splunk's index is Cruz-suggested, not a bare dropdown.

02

One wizard shape, every connector

Every connector runs through the same shell: breadcrumb, step counter, progress rail, one fixed primary-action position. Familiarity compounds across a ten-source session.

Built: both bespoke pairs and twenty-plus other connectors share one OnboardingWizard. Non-bespoke connectors run off a single generic wizard driven by a config object; adding connector 21 is a data change, not a new screen.

03

Two-tier guidance, not a knowledge-base tab

Ambient inline hints cover the obvious majority. Cruz, reachable from any field and pre-seeded with what the customer was looking at, covers the rest.

Built: Cruz's panel reads live session state, current step, filled fields, prior choices, so a question gets a step-specific answer instead of a generic one.

04

No silent waits, anywhere

A working system that doesn't say so is the same black box an SME exists to patch around.

Built: a shared live-test component shows real incoming sample lines the moment they arrive, live proof rather than a bare checkmark. The customer stays in control, one Continue click confirms it. On failure the component hands over a specific checklist plus retry and a non-blocking "continue, I'll send a sample later."

05

Rules stay visible, never a gate

Onboarding never asks for rule approval to proceed. At 900+ rules that would recreate the click problem one order of magnitude bigger.

Built: Pipeline overview groups active rules into five categories, each with a plain-language reason and a live before/after sample. Every count recomputes live as rules are toggled.

03

Navigation & hierarchy

  • Persistent left rail (Dashboard, Sources, Destinations, Pipeline, Search, Graph) visible everywhere, collapsible without losing labels.
  • Dashboard orients, Pipeline works. Dashboard answers "what needs me now," its funnel preview is explicitly labeled so it's never mistaken for the interactive version.
  • Fixed wizard chrome. Same breadcrumb, step counter, and progress-rail position at every step, every connector.
  • One decision per screen. A step asking two unrelated things is a defect, not a shortcut.
  • One heading style, one metric tile app-wide, with color reserved for tiles that have a real good or bad state to report.
04

Click reduction

Every click on the first-time, defaults-accepted path, from picking the connector to a live pipeline.

Palo Alto to Sentinel

12 clicks, source to live pipeline
  1. Select Palo Alto1
  2. Accept listener defaults1
  3. Accept log-type selection1
  4. Confirm after deploy1
  5. Live test, then Continue1
  6. Accept field mapping1
  7. Route to a destination1
  8. Select Sentinel1
  9. Sign in with Microsoft1
  10. Redirect, then Continue1
  11. Live test, then Continue1
  12. View this pipeline1

Entra ID to Splunk

12 clicks + 2 pasted fields
  1. Select Entra ID1
  2. Sign in with Microsoft1
  3. Redirect, then Continue1
  4. Accept scopes1
  5. Accept log categories1
  6. Live test, then Continue1
  7. Accept field mapping1
  8. Route to a destination1
  9. Select Splunk1
  10. Paste HEC URL + token, Continue2 fields + 1
  11. Live test, then Continue1
  12. View this pipeline1

Two mechanisms keep that count low. Session reuse means a second source routed to an already-connected destination skips setup entirely, one click instead of the four or five above. Accepted defaults stand in for what would otherwise be several separate field entries, a single Continue confirming a proposed port, scope list, or table name instead of typing each one. Every test step still ends on a manual Continue, by design, the live proof is worth a deliberate look before moving on, not a click removed for its own sake.

05

In-product guidance

A skippable coach-mark tour offers itself once on first visit, replayable later from the header. The distinction that matters isn't the panel, it's what Cruz already knows when it opens: current step, filled fields, prior choices this session. That's the real difference between in-product documentation and a search box that happens to live inside the product, the second one still makes the customer re-explain where they are.

07

What's simulated

This is a client-side prototype with no backend, built to be demoable live. Dollar figures use a published-list-rate table, labeled as an estimate with the rate shown, never presented as a real invoice. Live-test timings are compressed from the plan's real figures so a walkthrough doesn't cost real dead air. The same disclosure appears in the product itself, not only here.
